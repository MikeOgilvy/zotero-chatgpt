# zotero-chatgpt：端到端修复、重构与交付指令

你直接在当前 zotero-chatgpt 仓库中执行。目标不是写一份新架构文档，也不是只修几个按钮，而是把产品的核心用户流程做通，并主动解决妨碍使用的交互问题。

我不逐文件审查代码。你承担实现、测试、代码审查、真实宿主验证和交付责任。普通技术决策自行完成，不要反复让我选择目录、框架或实现方式；但不要把这种工程授权理解为可以随意修改我的真实文献库。

## 1. 产品要求：这些不是可以自行更改的假设

项目名为 zotero-chatgpt，产品位于 Zotero Reader 的 sidebar，有两个平级模式：

**Chat：**接入真实的 ChatGPT 官方网页，使用网页普通对话路径，不通过 Codex 发起模型请求，不要求 API key，不增加 API 计费。Chat 可以理解文献，但不能执行 Zotero 文献库写入。这里的“不消耗 Codex 额度”不等于承诺 ChatGPT 没有自身使用限制。

**Agent：**通过 Codex 执行对话和操作任务，能够调用受控的 Zotero 工具，真正创建高亮、添加笔记、打标签、整理集合。不能只用文字说“已经完成”。

两种模式都默认识别当前打开的 PDF 和选中文本，不要求用户反复上传、指定路径或输入“读取当前论文”。在首次使用时说明内容将发送到哪个服务，提供关闭自动附带当前文献的入口；不要后台上传整个文献库。

默认进入 Chat。用户明确切换才能进入 Agent。不能因为问题复杂、涉及 PDF、需要长上下文或 Chat 出错就自动调用 Codex。Chat 不可用时明确说明原因，不得偷偷改用 API、Codex 或外部网页跳转并声称完成原目标。

保留 New chat / New agent，不要求标题必须是论文标题。切换模式保留本地会话、草稿和用户上下文；每条消息记录实际执行模式。两个服务的远端会话标识分别维护，不假装它们天然共享历史。

## 2. 先验证最重要的接入事实，再大规模重构

先阅读现有代码、AGENTS.md、当前产品文档、测试和最近变更。查明实际 Zotero、Codex 和相关依赖版本，不要凭记忆假设宿主 API 或协议可用。

以本次明确的产品要求纠正过时文档；保留明确受保护、且与本次要求不冲突的约束。简短记录当前三条核心链路在哪一步断开，然后立即着手修复，不要陷入重新写一套文档体系。

Chat 必须分别验证以下三件事：

1. 在目标 Zotero 宿主中，官方网页能否正常加载、完成登录、保存会话并在重启后恢复。
2. 能否进行真实提问、接收真实回复，并验证流式显示、停止和历史恢复。
3. 当前 PDF / 选区是否通过实际可用的方式进入同一条真实对话，而不只是被插件本地读取。

本地 PDF 提取成功、网页打开成功、一个 mock 回复成功，均不能替代上述完整链路。用包含随机唯一内容的合成 PDF 验证真实回复确实使用了文档。

先验证最小链路，再扩展 UI 和迁移范围。不要先完成一大套 ChatClient 抽象，最后才发现没有实际可用的后端。

不得虚构“使用 ChatGPT 订阅的通用聊天 API”；不得通过抓取其他客户端 token、调用未公开端点、绕过认证或关闭宿主安全机制来制造成功。不要把 ChatKit 或 Codex 登录直接当成普通网页 ChatGPT 的替代品。

若网页嵌入、登录、上下文传递或历史桥接受平台限制，记录版本、复现方法、已验证结果和具体阻塞点。将受影响能力标记为 BLOCKED；不要反复碰运气，也不要掩盖限制。继续完成不依赖该阻塞的任务，但不能宣称完整产品已经交付。

已有本插件的有效登录会话可正常复用；没有时，先准备好能自主完成的实现、测试和安装流程，再集中提出必要的官方登录操作。不要索要密码、验证码、cookie 或 token。需要人工登录不等于需要人工帮你调试。

## 3. 架构边界：拆执行路径，不只是拆按钮

尽量保留现有有效结构；必要时可以跨模块重构，但不要为重构而重写。

逻辑上必须满足：

    Sidebar / Conversation UI
        ├── Chat → ChatGPT Web integration
        └── Agent → Codex integration → Zotero tools → verified changes

    Shared read-only DocumentContext → 两种模式

Chat 的加载、登录、提问、上下文处理、标题生成、历史恢复和错误重试，都不得暗中启动 Codex 任务。Chat 的可用性不得依赖 Agent 登录、Codex 安装或额度状态。

Chat 可以保存插件自己的会话、缓存和设置；“只读”限制针对 Zotero 文献数据、附件和原生标注，不是禁止一切本地持久化。

共享 DocumentContext 负责文献身份、附件身份、版本、页码、全文/选区和可用性。发送时固定本次请求的文档快照；切换 PDF 不得让正在执行的任务突然改为另一篇论文。缓存和异步结果必须按文档身份隔离。

Agent 的所有 Zotero 写入经过可验证的工具入口和权限检查。禁止绕过 Zotero 写入接口直接修改数据库；禁止给远程网页开放任意文件访问、执行代码或无限制写入能力。

PDF、网页、模型输出和工具返回的文本都是数据，不能把其中的指令当成用户授权。跨进程/网页桥接应限制来源、校验消息格式、绑定会话和操作范围，不把凭据写入日志。

模块、文件名、内部接口由你根据仓库决定。不要为了套用上面的示意图制造不必要的服务、队列、通用 provider 平台或插件框架。

## 4. 优先打通三条核心用户流程

### A. Chat：打开论文即可问

打开一篇 PDF → 打开 sidebar → 默认 Chat → 输入“这篇文章的主要贡献是什么？”→ 获得基于当前文献的真实回复。

继续支持选中文本后解释、追问、停止、重试和恢复会话。输入区说明实际附带的是全文、选区还是部分片段，以及是否传递成功；只有真实传递成功才能显示“已附带”。

长文档不能静默截断后装作看过全文。扫描件、提取失败、缺少图片理解能力、附件丢失或上下文超限，都要明确显示当前可用范围。不要把纯文本提取描述为读懂了图片和公式。

Chat 中收到“帮我高亮”时，可以提示切换 Agent，但不能自动执行写入或自动升级模式。

### B. Agent：真正圈划当前论文重点

用户切换 Agent，输入“高亮当前论文最重要的 5 处内容，并简要说明原因”。

完整链路必须是：读取当前文献 → 模型选择相关原文 → 程序匹配原文并解析真实位置 → 创建原生标注 → 读回验证 → 在 Reader 中可见并可定位。

模型可以提出原文片段和理由，不能把模型编造的页码、坐标直接用于写入。原文匹配不唯一、位置不可靠或内容不存在时，应跳过并说明，不能随意高亮一个位置凑数。

标注必须绑定正确附件，支持跨行文本，并验证缩放、旋转和重开后的定位。重新打开 PDF 后标注仍然存在，且可以撤销本次任务创建的标注。

重试和恢复不得重复写入。执行一半失败时，报告哪些成功、哪些失败；停止不能被描述成已经自动撤销先前完成的写入。

### C. Agent：真正整理选中文献

用户在 Zotero 中选中若干文献，要求“按主题打标签，并归入合适的集合”。

识别明确的选中范围 → 提出具体变更 → 必要时一次性预览确认 → 执行 → 读回标签和集合关系 → 给出可定位结果和撤销入口。

默认只作用于用户指定或选中的文献，保留已有标签和集合关系。目标不明确时只问影响操作范围的关键问题。

明确请求范围内、可撤销的新增操作不必逐条弹窗。删除文献、合并条目、覆盖已有内容、移动/删除附件、扩大到整个文献库等操作必须单独获得明确授权。

## 5. 主动完成交互，不等我逐个发现问题

从“首次安装 → 登录 → 打开文献 → 对话 → 切换模式 → 执行任务 → 停止/恢复 → 重启”完整走一遍，修复阻碍这条流程的问题。

重点处理：模式按钮不能点击、状态互相污染、输入丢失、中文输入法误发送、重复提交、流式内容乱序、自动滚动抢位置、侧栏宽度不足、阅读器焦点被抢、关闭侧栏后无法恢复、错误后按钮永远不可用。

发送、停止、重试、复制、新建会话和模式切换，都要有真实对应的状态和行为。登录中、提取中、生成中、等待确认、执行中、已停止、失败、已完成必须可区分。

不支持的功能不要放一个看似可用的假按钮；暂时禁用时解释原因。正常用户不应为了使用发布版手动启动 Node、Codex 服务、填写端口、复制凭据或操作开发脚本。必要运行组件应由插件管理；无法做到的环境应明确列出限制。

保持 Zotero 原生风格和清晰的信息层级。先完成可靠的核心交互，再做装饰、动画和额外设置。

## 6. 自主开发、自主审查、自主验证

在可恢复的开发分支或隔离工作区中工作，先检查并保留未提交改动。允许修改错误抽象、删除已证实无用的旧代码、更新相关测试和文档；不允许删除用户数据、重置无关改动或破坏 Git 历史。

先复现关键故障，为其建立回归测试，再实现修复。按真实用户流程逐步完成，而不是所有模块同时大改、最后一起猜是否能用。

优先使用仓库已有测试和宿主验证工具。测试数据、测试 profile 与真实文献库分离；发布包不得依赖测试 driver、mock 服务或开发环境中的偶然状态。

实现后安排一轮专门检查实际 diff 的审查，重点找接入错误、模式串线、权限越界、数据丢失、重复写入、异步竞态和假成功。可以使用可用的独立审查 agent；没有时明确是自审，不伪称已独立审查。

你负责修复审查发现的问题并重跑相关测试，不要只把问题清单交给我。不得删除断言、跳过失败测试、放宽完成条件来获得“全绿”。

普通工程问题自行解决。只有真实登录/系统授权、无法从仓库确定的关键产品冲突、或不可逆数据处理，才需要向我提问。环境限制要具体，不要用一句“需要人工验收”代替可完成的验证工作。

## 7. 必须留下可核查的验收证据

至少覆盖下列情况，并对每项分别记录结果与证据：

| 场景 | 必须检查的结果 |
| --- | --- |
| 干净环境安装发布包 | 能加载，无必须手动运行的开发组件 |
| Agent 未登录或运行时不可用 | 不因此阻断 Chat；Chat 自身问题单独报告 |
| Chat 真实提问 | 请求走官方网页路径，不触发插件的 Codex 任务 |
| 当前 PDF 作为上下文 | 真实回复能引用合成 PDF 中的随机唯一内容 |
| PDF A/B 快速切换、多窗口 | 请求、回复和缓存绑定正确文献 |
| Chat/Agent 来回切换 | 草稿和本地会话保留，执行身份不混淆 |
| Agent 高亮 | 原文、附件、页码和位置正确；保存后可读回、重开可见 |
| Agent 整理 | 只改变授权范围，原有关系按策略保留 |
| 超时、取消、重试、进程中断 | 无重复写入；已完成、未完成和未知状态可区分 |
| 撤销 | 只撤销本任务的变更，不覆盖用户后续修改 |
| 登录过期、网络失败、额度不足 | 提示真实原因；不静默换服务、模型或执行模式 |
| 重启 Zotero | 会话和任务状态合理恢复，不重复提交任务 |

验证 Chat 与 Codex 隔离时，同时检查静态依赖和运行时调用路径。记录插件触发的进程、任务和模型请求；不要仅根据按钮名称、工具列表为空或额度数字暂时没变化判断成功。隔离测试应覆盖标题生成、压缩、恢复和重试等隐藏路径。

自动测试、真实 Zotero 宿主测试、真实服务测试、最终发行包测试分别报告，不要混成一个“测试通过”。每项标注 PASS / FAIL / BLOCKED / NOT RUN，并附命令、实际结果和证据路径。

截图只能证明可见状态；写入成功还需读回验证。构建成功、类型检查通过、mock 端到端测试通过，都不能证明真实 Chat 或真实 Agent 已跑通。

如果当前环境没有可用 GUI、账号或网络，完成其余可执行验证，明确哪些能力仍未验证。不要编造截图、日志、成功回复或完成状态。

## 8. 交付与停止条件

交付可安装的 XPI、与当前实现一致的简短文档，以及实际测试记录。优先更新现有相关文档，不另建大量重复规划文件。

最终报告只需说明：

1. 原来核心流程为什么不通，实际修复了什么。
2. 三条核心流程分别在哪个验证层级通过，证据在哪里。
3. 发布包位置、支持/实测环境和必要安装方式。
4. 尚未通过或受阻的内容，以及需要我的最少操作。

我希望只参与必要登录和最后的使用体验反馈，不负责替你寻找编译错误、审查每个文件或验证你本可以自己检查的结果。

现在开始检查仓库并执行。不要只回复计划，也不要每完成一小步就问是否继续。按“关键接入验证 → 修复核心流程 → 交互完善 → 审查与回归 → 发行包验收”推进。

没有完成真实端到端验证时，就明确交付状态为部分完成或受阻；不能把改了很多代码当成产品已经可用。
