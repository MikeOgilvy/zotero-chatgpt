## 1. 必须保留的产品定位与执行边界

`zotero-chatgpt` 是一个 Zotero 插件，在 Reader 侧栏内提供两个平级模式：

| 模式 | 实际执行路径 | 本轮不可改变的事实 |
| --- | --- | --- |
| Chat | 官方 `chatgpt.com` 普通网页对话及受限页面桥 | 使用官方输入框和对话页面；插件不为其调用 Codex，不做 Zotero 文献数据写入 |
| Agent | 插件原生界面 → TypeScript core → Gecko 私有 stdio → 随包 Codex App Server | 使用 Codex 对话和受控操作能力；高亮、获取文章、整理文献仍需原有预览、批准和验证 |

Chat 与 Agent **不是同一个 Codex 对话的两个权限档位**。不能为了统一外观，把 Chat 重写成一个底层仍调用 Codex 的原生 composer。

Chat 的标题、摘要、上下文压缩、选区解释、恢复、重试和设置加载都不能暗中触发 Codex。Agent 不可用不能阻断 Chat；Chat 出错不能静默改走 Agent、API 或其它服务。

默认进入 Chat。切换模式是用户明确操作，不是授权自动提交、自动写库或转交草稿。两个模式保留各自的远端身份和历史，共享的是本地文献来源，不是一个虚构的远端会话。

“Chat 不使用 Codex 周额度”不是“所有服务无限使用”的承诺。不要显示固定额度数值、猜测的重置倒计时或无法核实的账户状态。

## 2. 已选定的视觉方向与设计基准

### 2.1 风格

采用**接近 Zotero / macOS 原生工具的安静、紧凑、清晰风格**。界面服务于论文阅读，不做营销页面，也不做一个缩小的后台管理系统。

重点是对齐、比例、层级、字体、留白、状态一致性和可预测操作。不要用渐变、玻璃效果、彩色大卡片、巨大 Logo、强阴影、装饰性动画或到处不同的圆角来代替设计。

官方 ChatGPT 内容区保留官网本来的样式。统一的是插件外壳、原生 Agent 界面、上下文详情、菜单、历史和 Preferences；不承诺两种内容区像素级相同。

### 2.2 数值基准

以下是本轮新增设计默认值，不是对现有实现的陈述。优先使用宿主已有语义颜色、字体和控件能力；缺失时使用统一的插件级 token，避免在每个组件里散落常量。

| 项目 | 默认设计基准 |
| --- | --- |
| 字体 | 系统 UI 字体，沿用宿主字体与用户缩放；不下载字体 |
| 普通控件文字 | 约 13 CSS px |
| 辅助说明 | 约 12 CSS px，不用极浅灰制造层级 |
| Agent 消息正文 | 约 14 CSS px，行高约 1.5–1.6 |
| 间距尺度 | 4 / 8 / 12 / 16 / 24 CSS px |
| 顶部工具栏 | 默认高度约 44 CSS px |
| 上下文摘要行 | 默认高度约 30–32 CSS px |
| 图标 | 16 CSS px，统一线性风格、视觉重量与对齐 |
| 桌面图标按钮 | 至少约 32 × 32 CSS px 命中区，不以压缩布局缩小点击区 |
| 圆角 | 小控件 6；菜单/卡片 8；原生 composer 12 CSS px |
| 分隔线 | 1 CSS px，弱于文字和主操作 |
| 动画 | 仅必要状态反馈，约 100–160 ms；尊重减少动态效果设置 |

常规宽度、默认字号下，顶部工具栏加上下文摘要以约 80 CSS px 内为目标；放大字号、窄窗、首次告知和错误详情可以重排，不能硬裁切来满足数字。

可用的回退色板如下。不要用全局样式覆盖 Zotero 本体或官方网页。

| 语义 | 浅色 | 深色 |
| --- | --- | --- |
| 外壳背景 | `#F7F7F8` | `#1E1F22` |
| 内容/输入表面 | `#FFFFFF` | `#27292D` |
| 主要文字 | `#1F2328` | `#ECEEF2` |
| 次要文字 | `#5C6470` | `#B0B5BF` |
| 普通边线 | `#D9DDE3` | `#464A52` |
| 强调色 | `#2563EB` | `#8AB4F8` |

主按钮的前景/背景需要成对设计，不要在深色主题的浅蓝按钮上照搬白字。正文与实际背景的对比度以不低于 4.5:1 为检查目标，重要控件边界与焦点指示以 3:1 为目标；不能只凭色板名称认为已满足。错误、成功和警告使用宿主语义色，同时提供文字或图标，不只靠颜色。

组件至少有 default、hover、pressed/selected、focus-visible、disabled 状态；涉及异步操作再提供 loading 和 error。不是每个状态都加一条常驻说明。

## 3. UI-01：一个稳定的共同侧栏外壳

把 Chat 和 Agent 放进同一个稳定的外壳，消除切换按钮在两种模式间上下移动的问题。

结构按下面执行，具体 DOM 与组件复用当前实现：

```text
┌────────────────────────────────────────────────┐
│ [ Chat | Agent ]   会话短标题    新建 历史 更多   │
│ 文献/选区摘要 · 下一次发送的实际范围          展开 │
├────────────────────────────────────────────────┤
│                                                │
│ Chat：官方 ChatGPT 页面，包含其官方输入框        │
│                                                │
│ 或                                             │
│                                                │
│ Agent：原生消息与任务内容                       │
│        原生 composer 固定在内容区底部           │
│                                                │
└────────────────────────────────────────────────┘
```

模式开关固定在顶部左侧；新建、历史、更多放在右侧。会话标题只占剩余空间，单行截断并提供完整名称，不得挤走模式开关。没有足够空间时优先缩短或隐藏重复标题，再将次要导航收入更多菜单，不移动模式开关。

模式标签保持 `Chat` / `Agent`。当前模式清楚可见，但不用大面积高饱和背景。正常状态下不用分别显示两套“Chat/Agent”标题。

**删除的是第二套模式控件，不是另一模式的能力。** Agent composer 底部不能再放同一模式开关；Chat 页面上方也不能保留另一个偏移位置的开关。

新建与历史明确作用于当前模式。有可靠实现时才显示为可用；没有真实接线的按钮不作为活跃控件交付。Chat 的插件历史入口标明本地绑定范围，不冒充官网完整历史。

实现必须保留官方 browser 与 Agent 会话的生命周期。不要每次切换都销毁 browser、重建服务、丢草稿或重新连接。隐藏区域不得抢焦点、接收键盘输入或覆盖另一模式的命中区域。

切换 Agent 的可用状态、显示任务状态、渲染 Preferences，不能成为新的模型调用入口。

## 4. UI-02 / UI-03：紧凑而准确的上下文与状态设计

### 4.1 顶部正常态只保留一条摘要

摘要优先回答：**“我下一次提问会附带什么？”**

显示真实来源的短标题或类型，以及最重要的范围信息。长文献名可截断，具体文本范围不能被一个笼统的绿色“Ready”替代。

可采用下列文案模式，根据实际数据选择，而不是硬编码示例数字：

| 实际情况 | 摘要示例 |
| --- | --- |
| 当前 PDF 文本片段已准备 | `Current PDF · excerpts from 3 of 24 pages` |
| 正在本地提取 | `Preparing current PDF text…` |
| 明确选区待发送 | `Selected text · page 5` |
| 自动 PDF 已关闭，无显式选区 | `Automatic PDF context is off` |
| 自动 PDF 已关闭，但有用户显式选区 | `Selected text · automatic PDF context off` |
| 没有当前 PDF | `No PDF context` |
| 文本提取失败 | `PDF text unavailable`，带详情入口 |

英文只是文案基准，同时提供现有中文本地化。若只能知道“部分文本”而不能证明具体页覆盖，就显示部分文本，不能编造 `3/24`。页标签和物理页索引按现有契约区分。

自动 PDF 开关关闭后，不再附带正文；显式选区仍可独立加入，并在摘要中清楚展示。没有 PDF 不应因此禁用普通 Chat。

### 4.2 点击摘要展开上下文详情

详情使用有锚点、可关闭、不会挤走整个对话的面板。常规尺寸可以用 popover；小高度/窄窗时用侧栏内有标题和关闭按钮的替代面板。不要再创建占满一屏的多层边框。

详情包含当前文献完整标题、来源、实际待发范围、选区/片段的可读预览、自动 PDF 开关和必要操作。提取统计、文件身份、覆盖限制等属于次级信息；内部 hash 和请求 ID 仅在技术详情中出现。

复制文献上下文、复制选区、重新提取、可选文件操作进入这里或更多菜单。没有选区就解释不可用原因，不渲染看似能复制但实际为空的按钮。

状态必须分开：

- 本地已经提取多少文本。
- 下一次准备发送什么。
- 上一次页面是否接受了那份消息。
- 是否出现了真实回答。

这四者不能拼成多条无归属的永久提示，也不能用前一个状态替下一个背书。详情里可以看上一条提交结果，但顶部摘要仍表示下一次来源。

### 4.3 反馈规则

普通复制/保存成功使用就近、短暂、可被辅助技术感知的反馈；连续相同消息合并，不堆叠成一排横幅。需要用户处理的错误保留一条明确原因和一个主要恢复操作，技术细节可展开。

不把刷新、复制成功、页面接受和后台提取各占一行。不要通过完全隐藏失败来获得“简洁”。用户关闭提示可以清掉视觉干扰，但不能抹掉底层错误状态或错误详情入口。

`Continue with current PDF` 只在真正存在当前阅读对象与对话上下文不一致、需要选择的状态出现。若保留，文案必须说明改变的是下一次上下文，不自动重发上一条问题。正常发送不依赖多一次“Continue”点击。

## 5. UI-04：Chat 网页与 PDF 附件的界面边界

### 5.1 Chat 内容区

官方页面尽量占用剩余可用高度。插件的顶部外壳不悬浮压在官方输入框上；正确处理 flex/grid 子项最小尺寸、browser 大小和滚动容器，不依靠写死窗口高度或全局 CSS zoom。

Chat 不渲染插件自己的第二个输入框、模型选择器、Agent 状态栏或网页已经提供的重复发送/停止控件。

页面加载、无法连接和接入异常可以有插件自己的紧凑状态，但登录页必须可操作。不要因为当前没有 composer，就把整个 browser 设置为不可点击。

**不要为了美观重写官网 DOM、隐藏官方消息、抓取回答、换成私有接口，或用 CSS 裁掉网站控件。** 允许调整插件拥有的容器，保持现有受限 actor 的 origin/frame、草稿、marker、冻结、接受确认与有界重试保护。

保留选区快捷操作的区别：`Ask in sidechat` 只准备选区与草稿，等待用户发送；`More details` 是用户明确触发的一次选区解释提交。它们都走同一个受限官方网页入口，不调用 Agent presenter 的模型路径，也不因为重新排版而变成重复发送。

截图中大段上下文出现在官方用户消息里，是可见提交路径的一部分。缩小插件顶部不会自动缩短这一官方消息；不能为得到“看不见上下文”的效果改成隐藏提交。真正的输入范围仍由现有预算和用户选择控制，本轮不借机重写上下文策略。

### 5.2 附件操作必须与真实实现一致

默认文本问答不要求手动附加 PDF；完整文件是用户主动选择的另一条操作。

若实际能力只是将 PDF 文件放到剪贴板，按钮采用 `Copy PDF file…` 一类真实名称，结果说明随后需要在 ChatGPT 粘贴。**复制成功不叫附件已上传。**

本地文件准备、官网出现附件、上传状态可确认，分别表示。无法可靠观察到的阶段，让用户在官方页面确认；不要为补状态而扩大页面读取范围。

文本片段与完整文件同时存在时分别说明。插件能控制的临时附件名称优先采用可读文献名，保留唯一身份映射；不重命名用户原始 PDF。

## 6. UI-05：完整设计 Agent 的原生界面，但不跑真实 Agent 功能

### 6.1 空状态与可用性

没有会话标题时使用 `New agent`，不是 `New chat`。空状态不做巨大的中心 Logo，也不只剩一个无说明的 `Model`。

在对话区上部或适度居中的紧凑区域放一个简短标题、一句用途说明，以及最多三个轻量任务入口：高亮重点、获取文章、整理选中文献。

这些入口只准备对应草稿或打开已有的必要范围选择界面，**不自动发送、不自动连接模型、不下载、不写库**。没有当前 PDF 的高亮入口、没有选中条目的整理入口，应说明缺少的来源；不要偷偷扩大范围补足条件。

不要为了填满空状态新增一个未实现的全网检索器、文献推荐系统或 onboarding 流程。

Agent 未登录、正在连接、未选模型、已知额度不可用、就绪等状态有明确文字。未知状态就是未确认，不从超时推断额度耗尽，不从随包目录推断账户可用模型。

本轮只通过离线注入的状态检查这些画面。未登录或额度不可用时仍允许用户编辑、保留草稿和浏览本地内容；不能把整个界面设为不可交互。

### 6.2 Composer

原生输入框与消息区分层，固定在 Agent 内容区底部，不覆盖最后一条消息，不随长消息被挤出窗口。

默认 composer 总高度约 96–120 CSS px；输入增长时自适应，文本区域通常到约 180 CSS px 或内容区高度的约三分之一后内部滚动。小窗口和放大字号下按实际可用高度调整，优先保证输入、发送和停止可达，不硬套数值裁切。

采用一套清晰结构：上方文本区；需要时出现来源/附件 chips；底部工具行左侧为已有附件或上下文操作，右侧为当前模型/生成设置与发送按钮。**这里没有 Chat / Agent 开关。**

模型选项来自已有缓存或本次明确取得的能力事实，不写死示例模型。缓存尚未确认时标明其状态；不得为打开下拉框或设置页面而连接真实 Codex。

发送、停止、排队和失败重试保留原有真实语义；一个按钮的图标、标签、可用性要一致。禁用时让用户知道原因，而不是只有灰色箭头或无标签圆点。

保留既有快捷键约定，明确 Enter 与 Shift+Enter；中文 IME 组合期间 Enter 不发送。任何替换文本或切换模式操作不得丢草稿、选区或光标位置。

### 6.3 消息与任务内容

原生 Agent 消息区以可读性为主。用户消息可用轻背景区分，回答优先使用清楚的正文排版，不必为每段文字套卡片或大头像。

保留已有 Markdown、公式、代码块、引用、图片和复制能力。长代码、公式或表格在自己的内容区域横向滚动，不把整个侧栏撑宽；普通正文正常换行。用户或模型提供的文本不能被当作 HTML/脚本执行，不能删掉已有内容安全处理。

只有用户在接近底部时才自动跟随新消息；用户已滚到旧内容时不抢位置，提供轻量“回到底部”入口。状态更新不要重建整个 transcript、composer 或 browser。

任务卡片复用现有任务记录，明确操作类型、冻结来源、候选数量和实际状态。预览展示原文、页码、理由和选择状态；一项任务可集中批准，不逐项弹窗。

批准、写入、读回、部分失败、uncertain、conflict、停止与撤销必须保持区别。不要用一个绿色勾覆盖未完成项，不显示伪造百分比或“已完成 5 项”的占位结果。

**开发过程中不要求我确认设计，不等于删除产品运行时对文献写入的批准。** 原有预览、批准、账本、读回与受控撤销全部保留。

卡片的 pending/review/running/completed/failed/uncertain 等画面可用明确的测试快照渲染。测试数据不写进用户历史、不调用原生写入、不进入正式产品默认状态。

### 6.4 模式切换与在途任务

切换模式分别保留草稿、会话、焦点和滚动。不要把 Agent 草稿自动塞进官网输入框，也不要复制官网历史来伪造统一会话。

在正常产品使用中，已有 Agent 工作不会因为用户显示 Chat 就自动停止或撤销。存在实际在途任务时，在 Agent 标签旁提供不改变开关尺寸的轻量提示与返回入口；不能使标签宽度跳动或掩盖仍在运行的工作。

本轮在途状态仅通过本地测试快照验证，不启动真实任务来观察动画。

## 7. UI-06：重新整理 Preferences 的信息层级

Preferences 是设置页面，不是第二个聊天工作台。使用统一标题、对齐的设置行、适度留白和细分隔线，替换截图中粗重 fieldset、巨大说明、失衡白色文本框和重复长列表的效果。

保留现有 Zotero 设置面板与偏好存储，不为此次样式改进创建独立设置应用、Web 服务或新的持久化系统。

按四组组织：

| 分组 | 内容 |
| --- | --- |
| General | 界面语言、实际支持的文字大小、自动文献上下文等共用偏好 |
| Chat | 官方网页接入说明和已有的网页相关插件设置；官网账号、模型仍由官网管理 |
| Agent | Codex 接入状态、模型白名单、生成设置、Agent instructions、skills |
| Data | 本地会话/绑定/缓存等明确范围的数据管理 |

默认设置行采用“左侧标签与一行说明，右侧控件”；宽度不足时自然上下排列。组间约 20–24 CSS px，行内约 8–12 CSS px，标题不使用大号营销字体。

模型列表使用紧凑行：勾选控件、可读模型名称和必要状态。原始 ID、目录来源和版本放入详情，不让每个 ID 单独占大段空间。不把未确认缓存包装成当前账户已授权模型。

`Codex instructions` 改为作用范围明确的 `Agent instructions`，说明“仅用于 Agent 请求”。文本区与所在列对齐，宽度合理，约 120–200 CSS px 初始高度；增长后内部滚动，不留截图中的巨大不对齐白块。

已有显式保存的多行内容保留明确 Save 与未保存状态；不要为了统一外观改成每个按键都写盘。已有自动保存的开关可继续自动保存，但失败要可见，不能把未持久化状态显示成已保存。隐藏设置区不能顺带清空其值。

skills 使用可读名称、启用状态和次级版本详情，不默认堆叠 `builtin · v1.0.0 · annotate`。没有已实现的安装能力，不添加假的“浏览 marketplace”入口。

字号按实际作用范围命名。例如仅控制原生 Agent 文本就叫 Agent text size；不要暗示它改变官方网页或 PDF 缩放。保持已有设置键与旧值兼容。

尊重用户已保存的界面语言；未设置时沿用仓库默认。同步维护现有中文与英文资源，Chat/Agent 产品名称不乱翻译，同一界面不要中英文标签混杂。

打开 Preferences、切到 Agent 设置分组或展开模型详情，不触发真实 Codex 探测。可显示明确标注的本地缓存或未连接状态。

## 8. UI-07：历史导航与数据管理分开

日常历史从侧栏顶部入口打开。沿用已有本地历史能力，调整为紧凑列表；Preferences 只保留数据管理，不再放完整聊天工作台。

历史行主要显示可读标题、Chat/Agent 来源、文献摘要与最近活动时间。正文不整段展开；长标题单行截断但可查看完整名称。搜索只搜索插件真正保存的字段。

已有当前论文/全部论文过滤可继续使用，但不要为了此次 UI 新建一个搜索系统。空列表、搜索无结果和载入失败要分别显示。

Chat 条目明确是本地绑定，不声称包含官网全部回答；旧 Codex `mode: chat` 不得被误标成官方网页会话或自动恢复。来源无法证明时显示旧记录/来源未知，保留原文件。

删除放在条目菜单或明确的数据管理操作中，说明删除的是本地绑定还是本地记录。删除本地 Chat 绑定不删除官网对话；删除 Agent 本地记录不撤销标注、不清账户、不删除上游线程。

保留活动请求/任务依赖检查。删除通过已有存储所有者执行，不在新列表组件里直接写 JSON 或删除文件。

本轮只用合成记录和受限测试存储验证列表交互，不清理实际用户会话。

## 9. 必须一起打磨的交互细节

这些是范围内工作，不要等我再逐个指出：

| 场景 | 预期行为 |
| --- | --- |
| 改变侧栏宽度 | 模式位置不跳；标题先缩短；控件不重叠；输入框不离屏 |
| 打开/关闭侧栏 | PDF 阅读锚点、缩放、旋转不变；已有草稿与会话不丢失 |
| 切 PDF 或 Zotero 窗口 | 下一次来源正确；在途请求仍显示自己的冻结来源；异步结果不串线 |
| 键盘导航 | 所有自有交互控件可聚焦；焦点可见；图标有本地化 accessible name |
| 关闭菜单/详情 | Escape 关闭当前层并把焦点交还触发控件；不关闭无关 PDF 或聊天 |
| 隐藏模式 | 不获取输入、不遮挡点击、不向屏幕阅读器暴露重复活跃控件 |
| IME | 组合输入不误发；输入不会因组件更新丢失或跳光标 |
| 流式/密集状态更新 | 不抢旧消息滚动；不重建 browser；不反复播报每个 token |
| 复制/保存/重试 | 有对应状态；无重复触发；失败后可恢复；不无限转圈 |
| 高倍文字缩放 | 允许重排；重要操作可达；不靠 CSS transform 缩回去 |
| 长论文名、长模型名、长错误 | 主要动作仍可见；详情可读；错误不把全屏挤满 |
| 未登录/离线/额度状态未知 | 显示事实和可执行下一步；不锁整个 UI、不伪造账户结论 |

工具提示不能成为唯一可达说明：重要禁用原因同时应能由键盘/辅助技术发现。不要为方便而给整个窗口挂会吞掉 PDF 快捷键的全局监听器。

菜单只对插件拥有的区域管理焦点与浮层。不要为了让浮层覆盖原生 browser 而关闭宿主安全机制；层级受限时采用侧栏内替代布局。

使用一个清楚的主滚动区；Agent composer 和公共头部不跟着消息滚走。允许代码块或展开详情在有明确边界时单独滚动，但不要造成整个侧栏与内容区重复滚动。

动效不能伪造进度。减少动态效果启用时，取消非必要过渡。遵循系统主题，避免切主题后仍残留浅色 input 或不可见的边框。

## 11. 本轮验证方案：不调用产品 Agent，也不省掉 UI 质量检查

### 11.1 先保证测试不会产生服务副作用

执行脚本前检查当前脚本的实际动作，不凭名字含 `test`、`context` 或“只读”就认为安全。

离线 UI 测试复用已有注入端口：账户、模型、会话和任务由明确的本地 fixture 提供。测试环境的真实 Codex process/connection/dispatch 入口设为拒绝，一旦触达就让用例失败。不要通过真的发一次请求再观察失败来证明没有调用。

在真实宿主中切换到 Agent 之前，先确认该测试路径的运行时已被安全隔离。生产实现允许的惰性连接不能在这次测试中意外启动。无法隔离时，Agent 外观只在离线组件/宿主 fixture 中验证，将真实连接场景记为 NOT RUN。

测试隔离只能用于测试装配，不增加面向普通用户的假服务模式，不在生产里强制 quota-exceeded，不把模拟会话/结果装入 XPI 默认数据。

### 11.2 执行范围

| 检查 | 本轮处理 |
| --- | --- |
| TypeScript、lint、无外部服务的已有 unit 回归 | 执行 |
| UI-01 至 UI-07 的组件、状态和交互回归 | 执行，使用本地数据与拒绝真实运行时的端口 |
| Chat 冷启动、通用设置、本地历史不调用 Codex | 用可用的静态/离线与无模型宿主证据验证 |
| Chat/Agent 的布局、主题、草稿、键盘、空状态 | 执行；Agent 使用隔离 fixture，不运行产品模型 |
| Agent 真实高亮、整理、下载、恢复、重试 | NOT RUN；用户本轮明确排除，Codex 周额度已用尽 |
| Agent 实际账户/模型查询、登录探测 | NOT RUN；不是本次 UI 验证的必要条件 |

不执行 `--context --live`、`--live-core-flows`、`--live-model` 或其它会连接产品 Agent 的等价入口。`--s5` / `--s6` 等未核对副作用的驱动也不能为凑覆盖率盲跑。

### 11.3 行为回归要覆盖具体故障

至少验证：模式开关只有一个稳定位置；切换不提交/串草稿；通用设置与模型缓存展示不连接 Codex；旧反馈不覆盖下一次上下文；关闭自动 PDF 后正文不再次自动加入；剪贴板动作不显示上传成功；中文组合输入不发送；新消息不抢旧消息滚动；保存失败不显示已保存；历史删除不触达原生撤销或账户目录。
