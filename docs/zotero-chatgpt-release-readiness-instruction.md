# zotero-chatgpt：发布前工程整备与开源交付指令

## 0. 任务目标与执行方式

直接在当前 `zotero-chatgpt` 工作树执行一次发布前工程整备：检查代码、目录、文档、测试、构建与发行材料，删除已经证实无用的内容，修正不一致，收敛不必要的复杂度，解决会影响用户和外部开发者的实际问题。

目标不是“文件越少越好”，不是再次推倒重写，也不是通过增加大量规范文件显得专业。最终应让人看得懂产品、找得到代码入口、照着文档能构建、出问题能定位，并能准确判断这个候选版本的可用范围。

**本指令授权本轮相关的源码、样式、测试、文档、构建配置与仓库清理，以及本地候选 XPI 的生成和核验。普通工程选择自行决定，不要求我逐文件确认、不反复问是否继续、不停在审计报告或计划。连续完成勘察、实施、回归、自审、文档核对与交付。**

本轮是“准备上线”，不是授权实际上线。不要自动提交 Git、改写历史、push、创建远端 Release（包括远端草稿）、发布 tag、签名、启用更新频道、修改仓库可见性或上传构建产物。不改变许可证选择、账户套餐或计费方式。

无法安全完成的外部步骤，记录具体 BLOCKED 原因，继续其余工作，最后集中说明；不要绕过权限，也不要因为一个步骤受阻就停止全部整理。

### 0.1 以当前工作树为准

先阅读当前根目录 `README.md`、`AGENTS.md` 和四份主文档：

本指令中的目录示例和检查项是待核验范围，不是已经发现的源码缺陷，也不是这些功能已经完成的声明。历史勘察中的路径、行号、测试数字与 a33 等版本标签不代表当前候选。

开始时记录当前基线与本轮预期修改范围；保留既有未提交改动。需要临时构建副本时，必须包含当前受检源码与尚未提交的相关变更，不能只复制旧 HEAD。不要用 `git clean`、破坏性 reset/checkout、批量删除或提交无关文件来制造“干净工作树”。

## 1. 已确定的产品方向：整理不能让它回退

### 1.1 执行路径不变

```text
Zotero Reader sidebar
├── Chat  → 官方 ChatGPT 网页 + 受限页面桥
└── Agent → 插件原生界面 → Codex → 受控 Zotero 任务

共享：本地文献身份、冻结 PDF 来源、明确选区
分离：远端会话、登录、请求执行、任务权限
```

Chat 不调用 Codex；标题、摘要、上下文压缩、选区、恢复和重试也不能暗中调用。Agent 才使用 Codex 的模型请求。Chat 不依赖 Agent 的登录、额度或连接状态；不能因 Chat 失败而静默改走 Codex、API 或其它服务。

官方网页拥有自己的输入框、登录与远端对话。不要为了简化架构或改善外观，把它换成调用 Codex 的原生聊天。不要读取生产网页回答或远端 transcript、复制认证、调用未公开端点或削弱现有桥接安全边界。

Agent 仍保留受限候选、预览、用户批准、写前意图、原生写入、读回、账本、对账与撤销。开发阶段无需我确认，和产品使用时需要用户批准文献变更，是两件不同的事。

### 1.2 最新 UI 与复制语义不变

保留并验证最近已经确定的方向，不再恢复旧的两行头部：

- 正常态为共同单行工具栏，Chat / Agent 位置固定；没有常驻 `Current PDF …` 行、旧按钮区或成功状态流水。
- 文献快捷操作只有 `Copy paper context` 与 `Copy PDF file` 两个图标按钮，说明可通过鼠标和键盘访问；必要导航继续保留。
- `Copy paper context` 复制本地标题、作者、发表载体、年份、DOI、摘要等真实必要信息，不复制 PDF 正文、选区、内部状态或模型总结。
- 手动复制与自动 PDF 上下文组装是不同路径。不能把真正发送的正文上下文也缩成只有 metadata + abstract。
- `Copy PDF file` 复制文件，不是路径，不等于已上传。两种复制动作独立判断可用性，使用点击时冻结的正确来源。
- Settings 与 Sidebar History 的本地删除双向同步；旧查询、旧保存或网页 URL 回调不能使已删记录复活。
- 保留独立草稿、焦点、滚动、PDF 阅读锚点、深浅主题、IME 与明确的本地数据删除范围。

本轮以核对、修复残余问题和清理旧实现为主；已经正常的布局、输入框和消息区不要重新设计。

### 1.3 项目展示不变

保留简短、英文、以用户价值为先的 README，沿用 `Read papers. Stay in Zotero.` 的方向；标题下方为后续真实 demo 保留位置。没有 demo 时使用不显示的注释，不生成假的视频、截图或空白占位块。

不能把“准备发布”写成“所有功能稳定可用”。Agent 的实验性、未验证流程和平台范围按实际证据表达，不删除限制来让 README 更好看。

## 2. 本轮测试与权限边界

沿用用户最近的明确限制：**本轮不调用产品 Codex，不试探 weekly limit，不执行真实 Agent 功能验收。** 用户未撤销这一限制；不要因为任务从 UI 扩大到仓库整理就自行恢复在线测试。

| 动作 | 本轮处理 |
| --- | --- |
| 源码/文档/配置整理、范围内重构、离线回归 | 执行 |
| 合成记录的持久化、删除同步、剪贴板、UI 状态测试 | 执行；只用明确隔离数据 |
| 本地构建、固定运行资产准备、XPI 校验 | 执行；先检查实际脚本副作用 |
| 无模型的专用 Zotero 宿主 UI / 加载检查 | 有条件时执行 |
| Agent 登录、账户刷新、实际模型查询、线程恢复、模型发送 | 不执行 |
| 真实高亮、整理、获取文章及原生动作功能验收 | 不执行；保留已有测试和功能 |
| ChatGPT 真实问答或文件上传 | 本轮不主动运行；页面/组装离线回归继续保留 |
| 日常 profile 安装、真实文献库或用户历史清理 | 不执行 |
| 付费 API、额外 Codex 审查会话、外发私有代码/资料 | 不启用 |
| 公开发布、远端提交、tag、Release、更新频道 | 不执行 |

这里的“Agent”指插件产品模式，不限制正在修改源码的开发助手正常编辑、构建和自审。但不要额外开一个会消耗 Codex 额度的开发或审查会话。

执行任何 test、prepare、install、release 脚本前检查实际行为与参数，不能凭名字判断无副作用。测试装配中拒绝真实 Codex process/connection/dispatch；需要展示 Agent 时使用明确的离线 fixture。该拒绝策略只能在测试装配中生效，不进入生产默认状态。

不要运行 `--context --live`、`--live-core-flows`、`--live-model`、`--native` 或等价功能入口。需要评估升级/回退时，先检查是否会启动 Agent 或执行原生任务；只运行已隔离、无这些副作用的子集，其余记为 NOT RUN。

依赖安装或已有固定资产下载不等于模型调用，但仍需遵守仓库既有来源、版本和校验规则；不增加新的计费路径，不上传私有文件以完成审查。

## 3. 先做短审计，然后立即实施

### 3.1 建立实际结构地图

核对当前源码入口、宿主注册、Chat 页面桥、Agent 装配、Reader 上下文、历史/设置存储、任务控制、样式、本地化、测试、构建与发行链路。

检查范围至少包括仓库实际存在的：

```text
packages/       生产代码与契约
runtime/        随包运行资产身份与配置
scripts/        构建、测试准备、安装、发行工具
tests/          离线回归、宿主驱动与合成 fixture
assets/locale/  或实际的样式、图标与本地化目录
.github/        已有 CI 与协作入口
根配置文件      package、lockfile、tsconfig、lint、manifest 等
README/AGENTS/docs
```

这些是职责示意，不要求照此新建目录。不存在的范围明确记录，不凭旧文档补造。

### 3.2 对候选清理项作决策

用一份简短工作清单记录 `保留 / 删除 / 合并 / 移动 / 修复 / 暂缓`，每项包含实际路径、理由、动态引用/兼容风险和验证方法。实施过程中更新，最终把有长期价值的结果归入现有文档，不把清单变成新的永久规范。

优先处理：发布内容泄漏或数据风险、错误执行路由、构建/安装阻塞、用户功能故障、明显维护负担，最后处理不影响行为的命名与格式。

不要以减少文件数、行数、依赖数或警告数作为成功指标。不要先花完整一轮只写审计，再要求我批准下一轮实施。

## 4. 仓库清理：删有证据的冗余，不删产品资产

### 4.1 可以清理，但必须逐项确认

检查并处理已经没有有效消费者的代码、旧 UI 分支、重复 formatter、重复状态转换、旧图标/CSS/locale key、临时 probe、一次性执行指令、过期计划、空 wrapper、注释掉的实现、无用依赖及重复配置。

删除前至少确认：

1. 源码调用、导出与测试引用。
2. 字符串注册、动态 import、JSWindowActor、XUL/XHTML、resource/chrome 映射及宿主回调。
3. 构建拷贝规则、package exports、脚本/CI、CSS 动态类名、本地化键与打包白名单。
4. 是否承担旧版本数据读取、取消/恢复、安全校验或故障回归。
5. 有效信息或替代行为已经落到正确位置，并有相应验证。

**搜索不到静态 import 不是死代码证明。** 文件名含 `legacy`、`compat`、`test`、`probe`、`codex`，或一个文件很大，都不是删除理由。

### 4.2 旧文档和历史材料

若 `repository-refactor-plan.md`、`zotero-chatgpt-codex-instruction.md` 或其它一次性旧工单仍在主文档路径，先迁移尚有效的契约、未完成事项和证据引用，再按具体文件删除并修复链接。不要恢复早期“Chat 也走 Codex”的规则。

不能把所有旧内容换个名字移进 `archive/` 后继续作为当前 agent 的默认输入。也不能删除唯一的失败报告、未提交的研究记录或没有其它可恢复副本的兼容说明。

只有实际确认某份材料已经进入可访问 Git 历史，才能用该历史替代当前重复副本；未提交/被忽略的本地文件不会因此自动有备份。历史失败可以从正文移到紧凑证据索引，但不能被改写成从未失败或被后续 PASS 覆盖。

### 4.3 生成物、敏感材料与发行内容分离

区分源码仓库、构建中间物、最终 XPI、宿主测试目录和用户运行数据。核查 `build/`、`dist/`、缓存、截图、临时 PDF、大型 fixture、备份、日志和测试 profile 是否放对位置、是否仍在被跟踪。

`.gitignore` 的存在不能代替跟踪清单核查。已经跟踪的生成物如需移除，按精确路径处理并保留必要的可恢复本地副本；不要因此清空整个目录。新的生成物应由脚本可靠生成，而不是手工提交后成为隐式构建前提。

不要清理用户的 `account/`、cookie、认证、现有 profile、真实历史或文献库。检查发布泄漏时，以构建白名单和受控源码/产物为范围，不递归扫用户电脑或读取运行账户目录。发现疑似敏感文件时，不打印内容，不放进公开报告；停止该文件的读取/打包，记录安全的分类与阻塞，不自行轮换凭据或改写 Git 历史。

随包运行二进制、第三方许可、必要 fixture、旧 schema 回归不是“大文件垃圾”。去留必须考虑运行依赖、测试目的和可重建性。

## 5. 代码整理：让外部开发者能顺着一条链路读懂

### 5.1 保留现有分层，明确责任

沿用实际的 `packages/zotero → packages/core → packages/contracts` 分层；core 不引入 DOM、Zotero 或 Node 运行依赖。宿主 API 留在适配层，Chat 页面桥不获得原生写入端口。

对当前确实混合多种职责的大文件作必要拆分，优先围绕真实职责：界面渲染、状态编排、宿主适配、持久化和纯格式化。拆分后应减少理解成本，而不是增加一堆只有一次转发的 service、manager、helper 或 `utils`。

不设机械的文件行数上限；不要为统一目录名大规模搬迁已经清楚的模块，不引入通用 provider 平台、DI 框架、新数据库、第二套任务/事件/会话系统。

### 5.2 单一事实来源与生命周期

重点复查并修正有证据的问题：

- 书目信息复制、自动 PDF 输入与正文预算是否各有清楚边界，没有“删重复”后误合并语义。
- Settings/Sidebar 的删除是否共用权威入口，提交后失效是否覆盖索引、打开视图、隐藏视图和计数。
- 旧查询、迟到保存、自动 URL 绑定是否可能恢复已删记录；按稳定 ID 与 scope 处理，不按标题删除。
- 订阅、定时器、DOM 监听、Observer、异步任务和进程是否有明确创建/销毁所有者。
- 多次开关侧栏/Preferences、切 PDF、多窗口、插件禁用/重新启用后是否出现重复注册、内存滞留或回调写入已失效视图。
- 旧 view/presenter 是否可以在关闭或替换后修改新文献、剪贴板或当前草稿。

先复现并定位，再以最小充分改动修复。不要把“多刷新一次”“每秒轮询”“延迟几百毫秒”“清空所有缓存”当作数据一致性的通用答案。

### 5.3 类型、接口、错误与注释

统一同一概念的命名，缩小不必要的 public surface，补齐真正跨模块的输入/返回类型。对不受信任数据在边界校验；内部已验证对象不必每层复制一套相同检查。

处理确有风险的 `any`、不安全断言、吞异常、未处理 Promise、无限重试与真假成功混淆。不要用更多 `as`、lint-disable 或 catch-and-ignore 掩盖问题；平台适配中的必要例外应有范围、理由和测试。

注释说明“为什么这样做”，尤其宿主差异、来源冻结、有限重试、旧 hash 兼容和撤销保护。删除过时注释、重复复述代码和“本轮修复了……”式开发流水；不要为了代码看起来整洁把关键原因也删掉。

新增或大幅修改的公开接口注释、错误文案和贡献者文档优先使用清楚的英文。中文/英文 UI 资源继续保留并同步，不顺手覆盖用户语言偏好。

### 5.4 兼容与高风险行为

保留旧 schema/hash 的可重建性、旧会话来源识别、任务快照、读回与撤销。旧 `mode: chat` 不等于官方网页来源。不要以“清理历史包袱”为由删除仍可能影响已有用户数据的读取分支。

pane ID、偏好键、插件 ID、存储路径、运行时 pin 和请求协议不为美化命名而改变。必要变更先给出兼容方案与离线回归；涉及无法在本轮验证的关键行为时保守处理，记录正式发布阻塞。

没有真实 Agent 测试条件，不代表完全不能改 Agent 相关代码，但不做大规模协议、原生写入、PDF 几何或恢复语义重写。确需修复的安全/数据问题以最小改动和可执行证据处理，不能据此宣称真实链路已验证。

### 5.5 性能优化必须有对象与证据

优先检查本地可观察的浪费：重复 PDF 提取/哈希、每次状态更新重建 browser/transcript、无界缓存、同步文件 I/O 阻塞 UI、搜索每键重复全量读取、监听器累积、重复渲染和无效后台工作。

对确有问题的路径记录修改前后相同环境、相同合成输入下的结果。记录版本、样本数和测量方法；没有测量不要写“快了 50%”“内存显著降低”。不为凑性能数字调用模型、增加大型基准框架或降低 PDF 身份与唯一匹配校验。

## 6. 文档整理：入口短，正文准，层级清楚

### 6.1 阅读路径与唯一维护位置

让两类读者各有最短路径：

```text
用户：README → 安装/使用 → 常见限制与问题 → 反馈入口
开发者：README/CONTRIBUTING → development → module-design → 相关源码与测试
```

优先整理现有文件，不重新创建十份内容重复的 onboarding/architecture/roadmap/plan。四份主 docs 的职责继续保持：

| 文件 | 本轮整理后的职责 |
| --- | --- |
| `README.md` | 英文产品入口：是什么、为什么用、demo、两种模式、怎么开始、去哪里看更多 |

### 6.2 README：继续克制

## 7. 依赖、构建与发行准备

### 7.1 依赖与脚本可理解、可复现

核查依赖真实使用、workspace 关系、工具链 pin、lockfile、安装脚本、运行资产来源和 hash。删依赖先确认源码、脚本、测试、构建和宿主路径都不再使用；同步 lockfile 后重新构建。

统一已有命令的职责与帮助信息，修复隐藏前置条件、互相矛盾的参数、脚本重复和产物选择问题。不要为了减少命令数量合并不同副作用等级的测试。

### 7.2 CI 与默认验证路径

优先修正现有 CI：离线检查、构建和 artifact verification 的默认路径不接触真实账户、Codex、私人数据或用户宿主。在线/宿主/模型测试应有明确、显式、独立入口，不能因普通 PR 或 push 自动执行。

检查测试的执行顺序是否依赖旧 `dist/`、缓存、未跟踪生成文件或偶然存在的运行资产。需要构建前置步骤就显式准备；不要用 skip 掩盖新 checkout 失败。

### 7.3 两种发布载体都要核查

分别检查“公开源码树/源码归档”和“XPI 白名单”中的内容，不只确认 XPI 干净就认为仓库也适合公开。

XPI 中只保留实际需要的生产代码、样式、图标、本地化、固定运行资产和许可。测试 driver、fixture 默认数据、认证、私有历史、合成问答、机器专属路径、开发开关与临时报告不能进入产品运行路径。确有开发辅助资产需要保留时，应说明具体用途与隔离方式，不用目录名猜测安全。

记录实际插件 ID、manifest 版本、平台/CPU 范围、运行资产版本、包名和 SHA-256，并核对相关文件一致性。不要将 workspace 版本、manifest 版本和 XPI 文件名强行视为同一个字段。

沿现有版本流程生成新的本地候选；不要自行升为 1.0、stable 或去掉 experimental。版本与发行文字不是质量证明。

### 7.4 从干净输入重建同一份受检代码

在不污染当前工作树的临时构建副本中，使用当前受检源码、lockfile 与明确运行资产重建；包含尚未提交但属于候选的变更，排除旧产物和未知本机文件。不要为构建副本复制认证、profile 或私人数据。
